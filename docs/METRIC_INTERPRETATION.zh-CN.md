# 指标问题解释、确认与上下文

认证模型保证查询使用已审核的定义和来源。它不能单独证明自然语言问题已被正确理解。因此 Chat 对模型提出的完整请求先返回 `confirmation_required`，展示指标名称、半开时间区间或全部历史、时区和业务时间角色、分组、额外过滤及排除条件、排序和行数上限。

用户可以直接补充修正条件，或点击 **Confirm and execute**。确认时提交最新待执行请求的 `confirm_query_fingerprint`，服务端只从当前用户拥有的会话历史读取完整请求，并重新检查模型版本、认证、权限、查询契约和物理来源。确认步骤不调用 LLM 改写请求；过期、不同版本、不同请求和已执行的确认不能重放。认证错误、权限错误和解释失败不会降级执行探索 SQL。

`trusted=true` 表示按认证定义执行；`intent_confirmed=true` 表示用户明确确认了该请求。历史记录没有后一字段时，界面明确说明未记录意图确认。解释 API 的 `ready` 仅表示结构化提案已通过编译校验，不是用户意图已经确认，也不代表查询已经执行。指标工作台仍由用户查看结构化表单后点击执行。

## 连续澄清

尚未形成完整请求的澄清链超过保留窗口时，不能静默丢弃原始客户排除、币种或时间条件。累计字符超限、超过五轮和单个超长回答会明确要求完整重述。之前成功的查询也不能替代其后尚未解决的新约束。

Chat 的 **Restate the complete question** 按钮为下一次输入设置 `reset_context=true`，建立持久化上下文边界。用户应在下一条问题重新给出全部范围和条件。之后的澄清不会重新继承边界之前的问题。客户端不能通过正文中的“已经确认”等话语创建可信的确认状态。

## 解释信息范围

已选择指标时，只发送该指标及组合依赖、可达逻辑字段、关系、业务时间和必要固定条件。指标 evidence、目录对象 ID、物理表列名称和结构指纹不进入解释提示。完整模型及其指纹留在服务端，编译和执行仍按完整认证模型验证。

较大模型未明确选择指标时，先以业务名称和描述发现候选，再加载候选及其指标族。候选发现不能自行解除口径歧义；未知候选、越出候选范围的提案和供应商错误直接拒绝。提示有 64,000 字符上限；超过预算要求明确选择指标，不截断业务定义。固定评测覆盖私密证据哨兵、指标族歧义和越界候选。

本批测试使用受控模型替身验证消息和错误提案，并在真实隔离 PostgreSQL/MySQL 5.7 上验证确认后的治理执行、会话持久化和权限。未连接真实 LLM 供应商，不能据此报告实际供应商 token、费用或自然语言正确率。跨请求追踪与用量统计另在 ENG-06 跟踪。
